# Exploit Farm

Farm has its own service catalog and team list. These are independent of Proxy listener configuration: a farm service's port is the destination port on a competition team, not a local reverse-proxy listener.

1. Add a service with its name and destination port.
2. Add each authorized team with its name and numeric IP address.
3. Add an exploit, select its service, and choose Binary, Python, or Bash.
4. Upload a file. For Python/Bash, alternatively select Paste code and paste the source. Click Save exploit once to upload and save its immutable version.
5. Choose a team beside the saved exploit and click Run, or use All selected teams. With no teams selected on an exploit, that means every enabled team. A schedule interval is optional.

IDs and source versions are generated by the UI. Binary uploads execute directly. Python source is saved as `exploit.py`; Bash as `exploit.sh`. Source changes create an immutable new version. Changing a Python version's dependencies requires providing source for a new version. Supported source size is 1 byte–2 MiB. Services/teams and exploit updates use revisions and record their authenticated author in the audit trail. Existing legacy target records remain usable through the API.

## Python and command arguments

Python uses the operator-configured `uv` executable:

```text
uv run --no-project --with requests --with pwntools==4.15.0 python -u exploit.py HOST PORT
```

Dependencies are optional, one package per line or comma separated in the UI. A registry package name or `name==version` is accepted, up to 32 entries. Requirement-file directives, URLs, local paths, and uv command options are rejected. An unpinned dependency follows uv's resolution rules; pin versions when repeatable environments matter. uv uses a private persistent cache. Initial dependency downloads require the host to reach the package registry. Installation errors are visible in stderr.

All runtimes receive the numeric target IP and service port as positional arguments. For example, Python can use `sys.argv[1]` and `sys.argv[2]`; Bash uses `$1` and `$2`. They also receive `HYDRA_TARGET_HOST`, `HYDRA_TARGET_PORT`, `HYDRA_TARGET_ID`, plus `TARGET_HOST` and `TARGET_PORT` aliases. `TARGETS_JSON` is an array of `{id,address,transport}`. Batch mode launches once and supplies `HYDRA_TARGETS_FILE`, a JSON file containing the selected target snapshots. Ordinary per-team mode launches once for each selected team, sequentially within the run timeout.

Example Bash source that only prints its configured destination:

```bash
printf 'Team %s at %s:%s\n' "$HYDRA_TARGET_ID" "$1" "$2"
```

## Host process execution

The operator selects the runner in the private operations JSON. To enable the host runner:

```json
{
  "execution_mode": "host",
  "host_runtime": {
    "uv": "/usr/bin/uv",
    "work_dir": "/var/lib/hydra-core/farm-host"
  }
}
```

Merge these fields with the existing flag/checker settings. The work directory must be absolute, owned by Core's OS user, and mode0700; its parent must exist. The uv path must be absolute. Host jobs are ordinary child processes running as Core's OS user, with the host filesystem and network access permitted to that user and the Core systemd unit. They do not use bubblewrap, a network broker, or per-job cgroups. Core clears inherited environment variables and provides a private working directory, home, and uv cache. Child process groups are killed on timeout, cancellation, or runner interruption. One worker executes at a time; the wall-clock timeout is enforced. The legacy manifest's CPU/memory fields apply to the sandbox runner, not individual host jobs. Core's service-wide limits also include its children.

The previous sandbox runner remains available with `execution_mode: "sandbox"` (the default when omitted). Host mode is an explicit product change requested for this deployment, not an automatic fallback when sandbox setup fails. The API accepts configured team IDs, never a hostname or arbitrary IP supplied to a run request. Queued runs snapshot team IP/service port; disabling or changing an endpoint before launch rejects that queued run. Host programs themselves have ordinary host network access.

## Host runner files and persistence

The current host runner creates these directories under `host_runtime.work_dir`:

| Path | Lifetime |
| --- | --- |
| `run-<random UUID>/` | Temporary working directory containing the copied entrypoint and optional targets file; removed when the run finishes |
| `home/` | Persistent `HOME`, shared by host jobs using this runtime directory |
| `uv-cache/` | Persistent uv package cache, shared by those jobs |
| `home/python/` | Persistent uv Python installation directory |

Ordinary relative-path writes land in the temporary run directory and are removed after completion. A host job can retain ordinary files under its `HOME`; those files belong to Core's OS user and are shared across jobs, not isolated per checker/exploit. The host runner currently provides no dedicated per-exploit `/state` mount. Back up the configured work directory if its home/cache contents matter. Traffic-filter workers have a different, per-checker persistent `/state` mount documented in [request checkers](REQUEST_CHECKERS.md#where-files-are-stored).

## Logs and rotation

Open Logs beside any run. Stdout and stderr are separate readable streams with target labels, state, timestamps, and exit code. The open view refreshes while execution runs. Host output is persisted approximately every300ms. Log payloads are stored as **zstd BLOBs** in Core's private SQLite database; the API decompresses bounded output for display. New logs clear the old plaintext columns. Completed legacy plaintext logs are converted in batches of up to64 records at startup and during periodic retention maintenance. Existing active plaintext records are not modified by that conversion.

Host stdout/stderr now stream into zstd chunks of at most32 KiB, with no1 MiB per-process capture cutoff. Flags are scanned throughout the stream, including after the old cutoff. The compatibility detail response contains only64 KiB previews; the console uses paged full-history reads and can follow the live tail or navigate earlier output. Original bytes are retained in chunks; API text uses UTF-8 replacement for invalid bytes and can split a multibyte character at a page boundary. The optional sandbox runner retains its existing per-worker output bounds; all available captured output from its targets is archived into the same chunks. Worker omissions remain explicitly marked.

Automatic retention keeps completed runs for at most7 days, at most1,000 completed records, and at most64 MiB of total stored compressed output, evicting the oldest when a limit is exceeded. Run deletion excludes queued/running runs and the active child. Chunk retention applies to active output too: the shared64 MiB compressed budget includes chunks and compatibility/legacy logs; a separate512 MiB raw chunk budget bounds highly compressible history. Oldest chunks rotate first, with absolute offsets and explicit dropped-byte metadata. Retention checks run periodically and after a run finishes. Cleanup is audited; deleted SQLite pages become reusable rather than requiring a database VACUUM during execution.

The UI can clean old runs immediately. The authenticated API also supports:

```text
DELETE /api/v1/farm/runs?older_than_days=7
DELETE /api/v1/farm/runs?older_than_days=0
```

Zero clears completed history immediately while preserving active work. Retry creates a new attempt with the original immutable source/manifest and target snapshot; rotated attempts no longer have a retry source. Run-list cursors now page newest-first by SQLite row position, while service/team catalog cursors remain ID based.

## Automatic flag queue and Python submitter

Open **Flags → Automatic flag submitter** (also linked from Farm). Enter the competition flag regular expression, paste or upload a UTF-8 Python script, and optionally list Python package names or exact `name==version` pins. Save with submission paused to collect flags without sending them. Enable when the script is ready. Settings are editable, revision checked, persisted in SQLite, and audited; the authenticated author comes from the session. The Farm regex changes immediately for future stdout/stderr scans and survives restart. Proxy defensive scanning retains its separately configured operator pattern.

Every eligible Farm match is deduplicated into the durable flag vault and submission queue, even while submission is paused and even if the legacy `auto_submit_captured` setting is false. Farm target/run provenance is preserved. The queue holds at most 5,000 pending flags; the vault at most 100,000. Existing defensive/own-exposed findings cannot enter this queue. Unknown proxy findings still require explicit triage; this feature does not automatically submit them. Changing the regex does not rescan old run logs.

Enabled submission picks up due queued captures within approximately one second while idle. Each automatic cycle takes up to the saved flags-per-call setting. Manual runs take a chosen snapshot of up to 5,000 flags, even while automatic submission is paused. See [Flags and submission](flags.md). A transient child runs the saved Python script through the configured host uv runtime:

```text
uv run --no-project [--with PACKAGE ...] python -u submit.py FLAG1 FLAG2 ...
```

Use `sys.argv[1:]` to read flags. Hydra adds no host/port arguments. Set flags per call from 1 to 240 (at most 60 KiB of flag payload). Manual runs split their chosen count into calls using this setting. Full regex matches are passed unchanged, including whitespace, case and Unicode; the entire match, not an individual capture group, is the flag. One submitter child runs at a time, independently of the single Farm worker. The script can read `HYDRA_SUBMISSION_BATCH_ID` for the current attempt. Dependency preparation is included in the configured timeout (1–120 seconds, default 20). The runtime uses Core's OS user and the explicit host runtime setting described above; inherited Core secrets are removed from the environment.

The script implements the actual competition checker protocol and interprets its reply. **Exit 0 means every flag in that call was accepted.** A nonzero exit, timeout, unavailable runtime, or interrupted attempt leaves flags queued for retry after at least 30 seconds; ten failed attempts mark them failed. Pausing or editing prevents subsequent chunks from starting with the old revision; a child already claimed may finish. On restart or persistence failure, interrupted claims recover to retry. An external checker may have accepted a flag before a script fails or Core stops, so the checker/script should handle duplicate submissions. Partial acceptance is not inferred from printed output.

The queue and paginated submission attempts are visible in Flags. Open Input / output on any retained attempt to see the exact input argument array and original stdout/stderr, including flag text. Hydra no longer replaces flags with [redacted flag] in new Python submission logs. Inputs and output are zstd compressed; output remains capped at64 KiB per stream. Completed attempts rotate after7 days,1,000 records, or64 MiB combined compressed inputs/outputs; audit records remain. Old redacted output cannot be reconstructed, and old attempts without saved inputs are labeled unavailable. Limits and retries are enforced by Core, independently of the Vue polling interval. Host uv package caches persist between runs and require normal operator disk maintenance.

Submission history uses authenticated `GET /api/v1/submitter/batches?offset=0&limit=20` (metadata summaries) and `GET /api/v1/submitter/batches/{id}` (full input/output); sensitive reads are audited. The generated OpenAPI describes authenticated `GET /api/v1/submitter`, revision-checked `PUT /api/v1/submitter`, and `POST /api/v1/submitter/run`. No internal gRPC or raw traffic contract changed. Existing private checker adapters remain supported until a Python submitter configuration is saved; a saved paused Python configuration keeps automatic sending paused.

For harmless end-to-end verification with real uv and a pinned dependency:

```sh
cargo build --locked -p hydra-core -p hydra-proxy
python3 tests/e2e/python_submitter.py
```

The fixture starts its own Core/Proxy with temporary databases and loopback-only configuration. It prints synthetic flags, tests collection/acceptance/retry/restart and original zstd input/output, and never contacts a competition service or checker. It advances only its own retry timestamps to avoid waiting through retry backoff.

## Process flag counts

Run rows show **New flags** and **Existing flags**, with per-target counts under
Logs. Counts represent distinct flag values per run/target: a new value was first
inserted by this process; an existing value was already captured elsewhere.
Repeated scans or repeated occurrences of the same flag in one process do not
inflate counts. Two processes printing the same new flag count it as new for the
first committed capture and existing for the other. Zstd-compressed output retains all
occurrences. Counts update as stream capture commits and survive restart.

Pre-update runs can recover known new flags from retained capture provenance,
but their duplicate history is unavailable: an asterisk/partial notice identifies
them. Observation metadata holds no extra plaintext flag values, is capped at
one million distinct run/target/digest records, and cascades away with run
retention. The quota fails explicitly rather than inventing counts.

Full output API: `GET /api/v1/farm/runs/{id}/logs?stream=stdout&offset=0&limit=65536`.
The response includes `text`, `start_offset`, `next_offset`, `end_offset`, `done`,
`dropped_bytes` and `history_lost`. Offsets count original bytes; request pages
until done, using next_offset. A rotated requested offset clamps to retained
history and sets history_lost. Completion waits for pipe drain/finalization even
when a cancellation status has already been committed. Reads are authenticated
and audited. Legacy truncated logs remain readable; their lost bytes cannot be
recovered.

## Runs table and log modal

Runs display **Run time**, **Team**, **Exploit**, **Service**, **Duplicate flags**,
**New flags**, **State** and **Actions**. Run time includes the start timestamp
(creation timestamp for queued runs) and elapsed execution duration, excluding
queue wait. Team cells list names and the IPs captured for that run; multiple
selected teams remain visible. Catalog names are resolved by Core even when the
exploit is on another editor page. Removed catalog entries fall back to IDs.

**Logs** opens a modal with run details, live stdout/stderr, paged retained output
and per-target flag counts. Close with Close logs, Escape or the close icon; focus
returns to the invoking button. Polling stops for log panels when the modal closes.

## Exploit effectiveness matrix

The Farm page includes a real exploit × team table, with independently paginated
20-row exploit/service and 10-column team axes. Filter by Farm service and runs
created in the last hour, 24 hours, seven days, or all retained history. Service
filtering happens before pagination. A deleted exploit remains represented while
its runs remain retained. Team identities distinguish legacy targets from the new
team catalog; deleted teams fall back to their captured names and IPs. Current
catalog names and hosts label headers; run logs retain the original endpoint.
A changed exploit service creates a separate row for its historical service.

Every populated cell shows run and recorded target-attempt counts, latest target
outcome and duration when available, distinct new/duplicate flag counts, accepted
flags, and a Logs action opening the existing run modal. A cell with no selected
runs says **No runs**; a run that produced no flags shows zero counts. The matrix
refreshes on demand, so it does not query SQLite while the page is hidden.

Actual target attempts are stored separately from aggregate runs. New per-target
host and sandbox executions record their start, end, state and exit code, with
millisecond timestamps. Sandbox attempt duration includes setup. Batch execution
records one shared process with an empty target identity: its result is never
presented as an individual team's result. Old runs without recorded attempts show
**Target outcome unknown**. Cancellation, shutdown and restart finish outstanding
recorded attempts with an appropriate terminal state. These outcome rows cascade
with run retention; migration0023 adds them without inventing historical outcomes.

Accepted credit uses the captured flag's original run and target plus its real
submission state. Seeing the same flag again does not give another cell credit,
and an exploit exiting successfully never implies checker acceptance. **Last
accepted capture** is the original capture timestamp of a flag now accepted, not
the time the checker answered. Captures in an older run stay outside a selected
run-creation window even if submitted recently. New/duplicate counts retain the
existing partial-history marker. Values and digests are absent from the matrix
response; opening the existing Logs modal remains an explicit diagnostic action.

`GET /api/v1/farm/effectiveness` accepts `service_id` (empty for legacy targets),
`window=1h|24h|7d|retained`, `row_offset` and `team_offset`. Omitting service selects
all services, and the default window is24h. Page offsets are bounded to20,000;
responses contain at most200 cells and next offsets. Reads authenticate and audit
the real requesting actor and selected filters. The API exposes aggregate run
fields separately from optional actual target-attempt fields; run timestamps are
seconds and target-attempt timestamps are milliseconds since the Unix epoch.
